## 一、整体架构：为什么系统要分三层？

### 1.1 先说一个生活例子

想象你走进一家大型图书馆：

- **图书馆入口**（L1）：有一个管理员，你问他"借书超期怎么办"，他立刻从胸前的本子里翻到答案，不用进图书馆里面查。**快，但只能答固定问题。**

- **图书馆内部**（L2）：如果入口管理员不知道（比如问"转专业选课冲突怎么解决"），你就要进图书馆内部搜索，书架上有上千本书，你要找到最相关的几本来回答问题。**慢，但能答复杂问题。**

- **图书馆管理委员会**（L3）：如果越来越多的人抱怨某个问题答得不好，管理委员会就负责去调查：到底是书架分类不对（检索问题），还是管理员没仔细看书（生成问题），然后修订规则或新增条目。**不直接服务用户，但让系统越来越聪明。**

---

### 1.2 我们的三层架构就是这个逻辑

| 层级 | 名字 | 核心职责 | 速度 | 成本 |
|------|------|---------|------|------|
| **L1** | 技能路由层 | 用规则精确匹配，直接返回固定答案 | < 10ms | 零 LLM 调用 |
| **L2** | Agentic RAG | 用向量检索 + LLM 生成答案 | 几百毫秒 ~ 几秒 | 调用 LLM（贵） |
| **L3** | 自进化技能层 | 分析错误，更新技能规则 | 不服务用户 | 分析 + 验证 |

**为什么要分三层？**

省钱。LLM 调用一次要花钱、要等时间。如果 80% 的问题都是常见问题（"图书馆几点开门"），每次都走 L2 成本太高。L1 用纯计算（不花 LLM 钱）过滤掉高频简单问题，只把复杂的交给 L2。

---

### 1.3 数据怎么从用户流到系统

```
用户问一个问题
    ↓
L1 接收到问题
    ↓
L1 用六维度评分，看看有没有技能能精确匹配
    ↓
    ├── 命中 answer_type=template？→ 直接返回预设答案（不走 L2）
    ├── 命中 answer_type=directive？→ 带着 L1 给的指令去 L2 检索
    └── 没命中？→ 去 L2 做向量检索
    ↓
L2 的 Quality Gate 评估检索质量
    ├── 质量够好 → LLM 生成答案，返回给用户
    ├── 质量不够 → 重检索（最多 3 次）
    └── 实在不行 → 标记低质量，返回答案（带标注）
    ↓
用户收到答案
    ↓
用户满意 → 结束
用户不满意（负反馈）→ 触发 L3 归因流程
    ↓
L3 归因：错误是检索层的还是生成层的？
    ↓
如果是检索层问题 → 修改/新增技能 → 冲突检测 → 验证 → 入库
    ↓
下次有类似问题 → L1 就能直接命中了
```

## 二、核心概念详解

### 2.1 什么是 Skill（技能）？

**定义：** 一个 Skill 就是一张"问题答法说明书"，用 YAML 格式编写。

每个技能包含：

```yaml
id: library_overdue_001          # 技能的身份证号（唯一）
name: 图书馆借书超期处理           # 人类可读的名字

trigger:                           # 触发条件：什么情况下用这个技能
  keywords: [借书, 超期, 罚款]   # 关键词：命中这些词就可能用这个技能
  aliases: [借阅图书, 图书归还]   # 同义词：这些词跟关键词意思一样
  semantic_type: procedure_query  # 语义类型：这是"流程类"问题

match_threshold: 0.6              # 匹配阈值：分数 ≥ 0.6 才算命中

answer_type: template             # 答案类型：template（预置答案）还是 directive（指令）
answer_template: |               # 预置答案内容（answer_type=template 时使用）
  图书馆借书超期处理流程如下：
  1. 登录图书馆官网或微信小程序
  2. 进入"我的借阅"查看超期书籍
  3. 按超期天数缴纳罚款（0.1元/天/本）

action:                            # 动作指令（answer_type=directive 时使用）
  retrieval:
    boost_keywords: [超期罚款标准]  # 检索时加权这些关键词
    filter_metadata: {category: library}  # 只在"图书馆"分类里找
    top_k: 5                       # 返回最相关的 5 篇文档

evolution:                         # 进化数据：这个技能的命中次数和成功率
  hit_count: 47                   # 被命中了多少次
  success_rate: 0.94              # 命中的用户满意率（94%）
  false_positive_count: 3         # 误报了多少次（不该用这个技能但用了）
```

**为什么这样设计？**

因为 YAML 人类可读、天认u可以直接编辑，Git 能版本管理。不用数据库，开发阶段改技能直接改文件就行。

---

### 2.2 什么是 SkillScore（技能评分）？

**定义：** SkillScore 是 L1 给每个技能打的分数，表示"这个技能有多适合回答用户的问题"。

公式：
```
SkillScore = Σ(wi × Di) / Σwi   （i = 1..6）
```
翻译成人话：**六维度的加权平均分**。

| 维度 | 变量名 | 算的方法 | 权重 | 什么意思 |
|------|--------|---------|------|---------|
| 关键词命中率 | D_keyword | 用户问题里的词命中了技能关键词几个？ | 0.25 | 命中越多，分越高 |
| 模式匹配分 | D_pattern | Aho-Corasick 多模式匹配得分 | 0.20 | 命中了多少关键词模式 |
| 语义类型匹配度 | D_semtype | L1 固定给 0.5（Phase 1 无法判断类型） | 0.20 | Phase 1 用固定值 |
| 同义词覆盖率 | D_alias | 用户问题里的词命中了技能同义词几个？ | 0.15 | 同义词覆盖越多越相关 |
| 历史成功率 | D_hist | 用这个技能历史上用户满意的比例 | 0.10 | 过去答得好就给高分 |
| 冷启动惩罚 | D_cold | hit_count < 10 → 0.8；否则 → 1.0（乘性系数） | — | 用的次数太少就扣分 |

**举例：** 用户问"借书超期罚款标准"

```
技能 library_overdue_001：
  keywords: [借书, 超期, 罚款, 归还, 借阅]

用户问题 tokens: [借书, 超期, 罚款, 标准]

D_keyword = len({借书, 超期, 罚款} ∩ {借书, 超期, 罚款, 归还, 借阅}) / len(keywords)
          = 3 / 5 = 0.6

D_alias = len({借书, 超期, 罚款} ∩ {借阅图书, 图书归还}) / len(aliases)
        = 0 / 2 = 0.0

D_semtype = 0.5（Phase 1 固定值）

D_hist = evolution.success_rate = 0.85

D_cold = hit_count=50 >= 10 → 1.0（不扣分）

SkillScore = (0.25×0.6 + 0.20×D_pattern + 0.20×0.5 + 0.15×0 + 0.10×0.85) / 0.90
           = (0.15 + 0.20×D_pattern + 0.10 + 0 + 0.085) / 0.90
```

---

### 2.3 什么是 match_threshold（匹配阈值）？

**定义：** SkillScore 的"及格线"。分数 ≥ 阈值，L1 才认为这个技能能回答问题。

```
SkillScore ≥ match_threshold → 命中，走 L1 预置答案
SkillScore < match_threshold → 未命中，去 L2 做向量检索
```

**当前 Phase 1 的问题：**

理论上阈值应该设 0.6，但实际代码里设的是 **0.4**。

为什么？因为 L1 的 D_semtype 维度固定是 0.5（Phase 1 无法判断语义类型），这导致最大得分天花板只有 0.725。如果用户问题只命中了部分关键词，D_keyword 和 D_pattern 自然偏低，综合得分通常落在 0.35~0.55 之间——根本达不到 0.6。

所以 Phase 1 临时降到 0.4，保证大部分简单问题能被 L1 截住、省下 LLM 调用。

**Phase 2 要做什么：**

等系统跑起来有了真实数据后，要把阈值逐步回调到 0.5~0.6。回调太快会导致很多问题漏到 L2（白花了 LLM 钱），回调太慢会让质量一般的答案通过 L1（用户体验差）。

---

### 2.4 什么是 Quality Gate（质量门控）？

**定义：** L2 里判断"检索出来的文档够不够好、要不要重检索"的关卡。

**为什么需要它？**

向量检索不是完美的，可能检索出来的文档和用户问题不太相关。如果直接让 LLM 基于差文档生成答案，答案质量肯定差。Quality Gate 就是 LLM 生成答案之前的"安检"。

**Q 分数怎么算？**

```
Q = α·S + β·M + γ·A + δ·C
```

| 指标 | 字母 | 算的方法 | 含义 |
|------|------|---------|------|
| 相似度均值 | S | `mean([doc.score for doc in docs])` | 检索出来的文档平均质量和问题有多像 |
| top-1 差距 | M | `docs[0].score - docs[1].score` | 第一名比第二名强多少？差距大说明越准确 |
| 文档一致性 | A | 文档向量两两余弦相似度的均值 | 检索出来的文档之间观点一不一致 |
| 关键词覆盖率 | C | 启发式计算 | 用户问题的重要词在文档里出现了多少 |

**权重（Phase 1 初始值）：**
- α = 0.40（相似度最重要，所以权重最高）
- β = 0.25
- γ = 0.20
- δ = 0.15

**Q 的决策逻辑：**

```
Q ≥ 0.75  → 通过，答案置信度高
Q ∈ [0.55, 0.75) → 灰色地带，通过但标记待验证
Q < 0.55 → 重检索（最多重试 3 次）
```

---

### 2.5 什么是 attribution_evidence（归因证据）？

**定义：** Quality Gate 输出的"诊断报告"，包含检索质量的各项指标，L3 用它来判断错误出在哪里。

```python
attribution_evidence = {
    "S": 0.62,                      # 平均相似度
    "M": 0.15,                      # top-1 和 top-2 的差距
    "A": 0.58,                      # 文档之间的一致性
    "C": 0.45,                      # 关键词覆盖率
    "Q": 0.58,                      # 综合质量分数
    "gap_type": "keyword_missing",  # 问题类型：关键词缺失 / 精度稀释 / 文档缺失
    "top_k_max_sim": 0.62,          # top_k 里最高的相似度
    "top1_sim": 0.62,               # 第一名文档的相似度
    "has_correct_entity": False,    # 文档里有没有正确答案的关键实体（人名/日期等）
    "reretrieve_count": 2           # 已经重检索了几次
}
```

**这个数据怎么用？**

L3 拿到这个报告，用"确定性前置筛"判断：
- 如果 `top_k_max_sim < 0.45` → 明确是检索层问题（文档相关性太低）
- 如果 `top1_sim > 0.80` 且 `has_correct_entity = True` → 明确是生成层问题（文档够好但 LLM 没好好用）
- 否则 → 模糊地带，交给 LLM 多裁判投票

---

### 2.6 什么是归因（Attribution）？

**定义：** 判断"系统答错了，问题出在检索层还是生成层"的过程。

**为什么需要归因？**

因为错误不同，修的方法不一样：
- 如果是**检索层问题**（文档本来就找错了）→ 修改技能里的 boost_keywords / filter_metadata / 新增文档
- 如果是**生成层问题**（文档找对了但 LLM 用得不好）→ 调整 LLM 的 prompt / 换模型

不归因就改，就像生病乱吃药。

**归因的两种方式：**

**方式一：确定性前置筛（零 LLM，速度快）**

看数字直接判断：
```
top_k_max_sim < 0.45         → 检索层问题（文档语义几乎不相关）
top1_sim > 0.80 且 has_correct_entity = True → 生成层问题（文档够好但 LLM 没好好用）
其他情况                         → 不确定，进方式二
```

约 50-60% 的情况可以跳过方式二、直接判定。

**方式二：LLM 多裁判投票（慢但准）**

对模糊情况，让 LLM 从三个角度看同一件事：
1. **文档充分性判断**：检索出来的文档内容足以回答这个问题吗？
2. **答案溯源判断**：正确答案的关键信息能否在文档里找到？
3. **断言对比判断**：错误答案里的哪些说法在文档里找不到依据？

三个 LLM裁判各自投票，取多数票。

**Phase 1 的安全约束：**
- 归因准确率 < 70%：只做人工审核，不开放自动修改技能
- 归因准确率 ≥ 70%：开放自动修改，但仍需人工审核才能入库

## 三、完整流程详解

### 场景：用户问"借书超期了罚款多少？"

#### 第一步：L1 接收问题

用户输入：`"借书超期了罚款多少"`

#### 第二步：L1 做两级精确匹配

**第一级：example_queries 精确匹配**

检查用户问题是否完全等于某个技能的 example_queries（比如"借书超期了怎么办"）。

本例：**不匹配**，进入第二级。

**第二级：token 精确匹配**

把用户问题切成词：`[借书, 超期, 了, 罚款, 多少]`

检查是否有技能的 keywords 完整等于这组词。

本例：**不匹配**，进入 SkillScore 评分。

#### 第三步：L1 计算 SkillScore

对每个技能计算六维度加权得分：

针对技能 `library_overdue_001`（keywords: [借书, 超期, 罚款, 归还, 借阅]）：

```
D_keyword = 3/5 = 0.6         # "借书""超期""罚款"都命中了
D_pattern = （Aho-Corasick 匹配得分，归一化）假设 = 0.55
D_semtype = 0.5               # Phase 1 固定值
D_alias = 0/2 = 0.0           # 没有同义词命中
D_hist = 0.85                 # 历史上成功率 85%
D_cold = 1.0                  # hit_count=50，够多，不扣分

SkillScore = (0.25×0.6 + 0.20×0.55 + 0.20×0.5 + 0.15×0 + 0.10×0.85) / 0.90
           = (0.15 + 0.11 + 0.10 + 0 + 0.085) / 0.90
           = 0.445 / 0.90 = 0.49
```

#### 第四步：L1 判断是否命中

```
match_threshold = 0.4
SkillScore = 0.49 ≥ 0.4  → 命中
```

#### 第五步：L1 返回答案

```
answer_type = template → 直接返回预置答案：

"图书馆借书超期处理流程如下：
  1. 登录图书馆官网或微信小程序
  2. 进入"我的借阅"查看超期书籍
  3. 按超期天数缴纳罚款（0.1元/天/本）"
```

**零 LLM 调用，< 10ms 完成。**

---

### 如果 L1 未命中，场景变为：用户问"转专业后学分怎么算？"

#### 第六步：进入 L2（因为没有技能匹配）

L1 计算后没有任何技能的 SkillScore ≥ 0.4，进入 L2。

#### 第七步：L2 的 Router 节点做什么

Router 用 LLM 判断用户问题的类型（policy_query / factual_query / procedure_query 等），并输出置信度。

本例：类型是 "policy_query"（政策规定类）。

#### 第八步：L2 的 Retriever 节点做什么

根据 L1 没有匹配成功的"感觉"，去 Qdrant 向量数据库里检索相关文档。

1. 把用户问题转成向量（Embedding）
2. 在 collection "campus_knowledge" 里做向量相似度搜索
3. 返回 top_k=5 篇最相关的文档
4. 加上 L1 技能的 boost_keywords（比如"转专业、学分"）做加权

#### 第九步：L2 的 Quality Gate 节点做什么

计算 Q 分数：

```
S = mean([doc1.score, doc2.score, doc3.score, doc4.score, doc5.score]) = 0.72
M = doc1.score - doc2.score = 0.78 - 0.65 = 0.13
A = mean([doc1↔doc2, doc1↔doc3, ...]) = 0.61
C = 关键词覆盖率 = 0.55

Q = 0.40×0.72 + 0.25×0.13 + 0.20×0.61 + 0.15×0.55
  = 0.288 + 0.0325 + 0.122 + 0.0825
  = 0.525
```

Q = 0.525 ∈ [0.55, 0.75) → **灰色地带**，通过但标记待验证。

同时输出 `attribution_evidence` 供 L3 使用。

#### 第十步：L2 的 Generator 节点做什么

把检索出来的 5 篇文档 + 用户问题一起发给 LLM，让 LLM 生成答案。

prompt 大致是：
```
你是一个校园知识问答助手。根据以下文档回答用户问题。
如果文档里有答案就基于文档回答，如果文档不够，不要乱编。
用户问题：转专业后学分怎么算？
文档：[...]
```

#### 第十一步：用户收到答案

```
"转专业后学分计算规则如下：
1. 原专业修过的课程学分可以申请认定为选修课学分
2. 核心专业课程如果已有相关内容可申请免修
3. 具体流程请咨询学院教务办公室"
```

用户满意 → 结束
用户点击"没用" → 进入 L3

---

### 如果用户给了负反馈（L3 归因流程）

#### 第十二步：L3 归因怎么做

假设上述答案用户不满意，点击了"没用"。

L3 拿到：
- `attribution_evidence`（Quality Gate 的诊断报告）
- 用户给的正确答案（用户填了"转专业后学分要全部重新修"）

**第一步：确定性前置筛**

```python
top_k_max_sim = 0.72
top1_sim = 0.78
has_correct_entity = False  # 文档里没有正确答案的关键实体

if top_k_max_sim < 0.45:         # 0.72 不小于 0.45，否
elif top1_sim > 0.80 and has_correct_entity:  # top1_sim=0.78 不大于 0.80，否
else:
    → 进入 LLM 多裁判投票
```

**第二步：LLM 多裁判投票**

三个视角的 LLM 裁判各自判断，两个说"检索层问题"（文档根本没找到正确答案），一个说"生成层问题"。

→ **归因结论：检索层问题**

**具体子类型：** 文档缺失（正确答案"转专业后学分全部重修"相关内容根本没有被检索到）

**修复动作：** 触发 ETL 补全流程（去学校官网抓取/录入转专业学分规定），同时给技能 `transfer_major_001` 的 `boost_keywords` 加入"学分、全部重修、转专业政策"等词。

#### 第十三步：L3 冲突检测

如果有另一个技能 `transfer_credit_001` 的 `depends_on` 和它有重叠，冲突检测器会计算冲突分数 C：

```
C = 0.4 × Jaccard(depends_on) + 0.3 × Dice(trigger) + 0.3 × Co_occur
```

- C ≥ 0.8 → **BLOCK**，阻止入库，人工处理
- C ≥ 0.65 → **WARN**，触发人工审核
- C < 0.65 → **OK**，允许入库

#### 第十四步：技能修改/新增，验证

候选技能生成 → 冲突检测通过 → **RAGAS 验证**（用标准评估指标判断新技能是否比旧技能好）

验证通过标准：`Δ = 新技能分数 - 旧技能分数 > 0`

通过后：写入 YAML → 版本号 +1 → 正式技能库 → 下次命中

## 四、公式详解

### 公式一：SkillScore（六维度加权平均）

```
SkillScore = Σ(wi × Di) / Σwi   （i = 1..6）
```

| 参数 | 值 | 含义 |
|------|-----|------|
| w1 = 0.25 | D_keyword 权重 | 关键词匹配最重要，所以权重最高 |
| w2 = 0.20 | D_pattern 权重 | Aho-Corasick 多模式匹配 |
| w3 = 0.20 | D_semtype 权重 | 语义类型匹配（Phase 1 固定 0.5） |
| w4 = 0.15 | D_alias 权重 | 同义词覆盖 |
| w5 = 0.10 | D_hist 权重 | 历史成功率 |
| w6 = 1.0 或 0.8 | D_cold 系数 | 冷启动惩罚（乘进去，不是加进去） |
| w_total = 0.90 | — | 五个加权项之和（D_cold 是乘性系数，不计入） |

**为什么是加权平均而不是直接求和？**

因为六个维度的量纲不同（都是 0~1），直接求和会导致维度数量影响总分。加权平均把每个维度归一化到 0~1 范围内，然后按重要性加权。

**D_cold 为什么是乘性系数而不是加性维度？**

因为冷启动惩罚的意义是"打折"——如果 hit_count 太少，整个得分都该打个八折。用乘法可以实现这个效果（D_cold = 0.8 时 SkillScore 直接 × 0.8）。

---

### 公式二：Quality Gate Q 分数

```
Q = α·S + β·M + γ·A + δ·C
```

| 参数 | 值 | 含义 |
|------|-----|------|
| α = 0.40 | S 权重 | 检索文档的平均相似度最重要 |
| β = 0.25 | M 权重 | top-1 和 top-2 的差距（margin） |
| γ = 0.20 | A 权重 | 文档之间的一致性（agreement） |
| δ = 0.15 | C 权重 | 关键词覆盖率（coverage） |

**为什么 M（margin）重要？**

如果 top-1 是 0.90、top-2 是 0.89，margin 只有 0.01，说明排名靠前的文档之间质量很接近，随便选哪个差不多。如果 top-1 是 0.90、top-2 是 0.50，margin 很大，说明第一名文档明显优于其他，置信度高。

**为什么 A（agreement）重要？**

如果检索出来的 5 篇文档都说的是同一件事，它们之间一致性高，说明检索质量稳定。如果有的说"转专业不换学分"，有的说"转专业全部重修"，一致性低，说明系统对这个问题本身就不确定。

---

### 公式三：冲突检测分数

```
C = 0.4 × Jaccard(depends_on) + 0.3 × Dice(trigger) + 0.3 × Co_occur
```

| 参数 | 含义 |
|------|------|
| Jaccard(depends_on) | 两个技能的依赖集合的交集/并集比值 |
| Dice(trigger) | 两个技能的触发条件的重叠度 |
| Co_occur | 两个技能在历史数据中同时被命中的频率 |

**Jaccard 和 Dice 的区别：**

```
Jaccard = |A ∩ B| / |A ∪ B|
Dice = 2 × |A ∩ B| / (|A| + |B|)
```

Jaccard 更保守，Dice 更容易给高分。如果 A={1,2,3}，B={2,3,4}：
- Jaccard = 2/4 = 0.5
- Dice = 2×2/6 = 0.67

## 五、Phase 1 vs Phase 2

### Phase 1（当前阶段，架构验证期）

**目标：** 验证三层架构能不能跑通，不追求真实效果

| 约束 | 说明 |
|------|------|
| 技能库封闭 | 只修改已有技能的字段（boost_keywords / match_threshold 等），不新增 skill ID |
| match_threshold = 0.4 | 临时降低，确保 L1 能截住更多请求（Phase 2 回调到 0.5~0.6） |
| 种子技能预设值 | hit_count=50, success_rate=0.85（Phase 1 演示用，非真实数据） |
| 归因需人工验证 | 归因准确率必须 ≥ 70% 才能开放自动修改，且入库仍需人工审核 |
| 不开放新增技能 | L3 只修改字段，不生成新技能 ID |

**Phase 1 的数据说明：**

```
⚠️ Phase 1 所有性能数据均为"架构验证演示数据"，不代表真实运营效果。
```

## 六、术语表

| 术语 | 英文 | 解释 |
|------|------|------|
| **RAG** | Retrieval-Augmented Generation | 检索增强生成。简单说就是先从文档库找到相关材料，再让 LLM 基于这些材料生成答案 |
| **Agentic RAG** | Agentic RAG | 智能体式的 RAG。能自主判断检索策略、评估质量、决定是否重检索，比普通 RAG 更"聪明" |
| **Skill** | 技能 | 一张"问题答法说明书"，包含触发条件、答案模板、检索配置等 |
| **SkillScore** | 技能评分 | L1 给每个技能打的六维度加权分数 |
| **match_threshold** | 匹配阈值 | SkillScore 的"及格线"，≥ 阈值才认为技能能回答问题 |
| **Aho-Corasick** | Aho-Corasick 算法 | 多模式字符串匹配算法，能一次性在一段文本里找出所有预设关键词 |
| **Quality Gate** | 质量门控 | L2 里判断"检索质量够不够好"的关卡，决定是否重检索 |
| **attribution_evidence** | 归因证据 | Quality Gate 输出的诊断报告，包含检索质量的各项数值指标 |
| **归因** | Attribution | 判断错误出在检索层还是生成层的过程 |
| **冲突检测** | Conflict Detection | 检查新技能是否和已有技能重复/矛盾 |
| **冷启动惩罚** | Cold Start Penalty | 新技能因为历史上被用得少而给的扣分（hit_count < 10 时 D_cold=0.8） |
| **Circuit Breaker** | 熔断器 | 一种设计模式，LLM 连续失败多次后"熔断"，暂停调用防止系统崩溃 |
| **指数退避** | Exponential Backoff | 失败后等待时间指数增长（1s → 2s → 4s），避免过度重试 |
| **RAGAS** | RAG Assessment | RAG 系统的标准评估框架，有 Faithfulness、Answer Relevance 等指标 |
| **LangGraph** | LangGraph | LangChain 的状态图编排库，用来写 L2 的节点流程 |
| **Qdrant** | Qdrant | 向量数据库，用来存文档的向量表示，支持高速相似度检索 |
| **向量检索** | Vector Retrieval | 把文本转成向量（Embedding），用余弦相似度找最相关的文档 |
| **Collection** | Collection | Qdrant 里的"表"，一组向量的集合 |
| **Embedding** | Embedding | 把文字转成一串数字（向量），让计算机能计算文字之间的语义相似度 |
| **hit_count** | 命中次数 | 一个技能被 L1 匹配到的次数 |
| **success_rate** | 成功率 | 命中后用户满意的比例 |
| **false_positive** | 误报 | 不该用这个技能但用了（答非所问） |
| **directive** | 指令 | L1 告诉 L2"怎么检索"的指令（boost_keywords / filter_metadata 等） |
| **template** | 模板 | 预置答案，用户问题命中后直接返回，不走 LLM 生成 |
| **semantic_type** | 语义类型 | 问题类型（policy_query / factual_query / procedure_query 等） |
| **ScaleRisk(t)** | 连续风险指数 | 根据时间/事件计算当前系统风险等级，决定验证深度 |

## 八、常见问题

**Q：为什么不所有问题都走 LLM 生成，要 L1 干嘛？**

A：成本和速度。LLM 调用一次几毛钱、几百毫秒。80% 的常见问题（图书馆规则、选课时间）其实是可以用固定答案的，L1 用纯计算 < 10ms 就返回了，省下的 LLM 调用成本很可观。

**Q：为什么用 YAML 而不是数据库存技能？**

A：Phase 1 开发阶段，YAML 可读可改、天认u直接编辑、Git 版本管理，比数据库更灵活。Phase 2 如果性能不够再迁数据库。

**Q：技能的数量会影响 L1 性能吗？**

A：Dict 精确匹配是 O(1)，Aho-Corasick 构建后匹配是 O(n)，n 是文本长度，和技能数量无关。但 SkillScore 评分需要对每个技能计算六维度，所以 L1 性能 ≈ O(技能数量)。当前 10 个种子技能，10ms 内没问题。Phase 2 如果有 100+ 技能，需要优化。

**Q：Phase 1 演示数据（hit_count=50, success_rate=0.85）会有问题吗？**

A：不会影响架构验证，但实验报告里要注明这是工程预设值，不代表真实运营效果。等真实数据积累后，这些值会从真实使用中更新。
