**项目定义：** 多源错误反馈驱动、可解释技能路由与分级验证闭环约束下的 Agentic RAG 技能进化框架

## 1. 架构总览

### 1.1 系统定位

EvoRoute-RAG 是一个**三层分流 + 自进化闭环**的校园知识问答系统：
- **第一层（L1）**：可解释技能路由层 - 零 LLM 调用，毫秒级响应
- **第二层（L2）**：Agentic RAG - LangGraph 状态图 + Qdrant 向量检索
- **第三层（L3）**：自进化技能层 - 错误归因 → 技能生成 → 冲突检测 → 分级验证

### 1.2 核心设计原则

1. **确定性优先**：L1 使用确定性算法（Dict + Aho-Corasick），可解释、可审计
2. **分级验证**：根据 ScaleRisk(t) 动态调整验证深度（低/中/高风险）
3. **闭环进化**：错误反馈 → 归因 → 技能修改 → 验证 → 入库 → 下次命中
4. **Phase 分界**：Phase 1 封闭技能库（只修改字段），Phase 2 开放新增技能

### 1.3 技术栈选型

| 层级 | 组件 | 技术选型 | 理由 |
|------|------|---------|------|
| L1 | 精确匹配 | Python Dict | O(1) 查找 |
| L1 | 多模式匹配 | Aho-Corasick | 多关键词并行匹配 |
| L2 | 状态图编排 | LangGraph | LangChain 生态标准 |
| L2 | 向量检索 | Qdrant | 生产级，支持分布式 |
| L2 | LLM | MiniMax API | OpenAI 兼容格式 |
| L3 | 评估框架 | RAGAS | 行业标准 RAG 评估 |
| 存储 | 技能库 | YAML 文件 + Git | 版本管理 + 人类可读 |

## 2. 第一层：可解释技能路由层（L1）

### 2.1 功能定义

L1 是系统的"高速公路"，用确定性算法实现：
- **零 LLM 调用**：纯符号计算
- **毫秒级响应**：< 10ms
- **可解释路由**：六维度 SkillScore 评分

### 2.3 SkillScore 六维度评分公式

```python
SkillScore = Σ(wi × Di) / Σwi   (i = 1..6)
```

| 维度 | 变量 | 计算方式 | 权重 |
|------|------|---------|------|
| 关键词命中率 | D_keyword | 对每个原始 keyword：若 query token 命中 keyword 本身或其任意同义词（查 synonym_dict），算1次命中；最终 D = 命中数 / 原始 keyword 总数（分母不膨胀） | 0.25 |
| 模式匹配分数 | D_pattern | Aho-Corasick 命中分 / (boost × 原始模式总数)；命中分母取原始 keywords + aliases，不含展开同义词（避免 boost 稀释） | 0.20 |
| 语义类型匹配度 | D_semtype | L1：`0.5`（Phase 1 L1 无法判断类型，固定默认值）；未来扩展可支持显式规则判断 | 0.20 |
| 同义词扩展覆盖率 | D_alias | `len(query_tokens ∩ aliases) / len(aliases)` | 0.15 |
| 历史成功率 | D_hist | skill.evolution.success_rate；种子技能预设 0.85（Phase 1 演示用，非真实数据） | 0.10 |
| 冷启动惩罚 | D_cold | `0.8` if hit_count<10 else `1.0`（乘性系数）；种子技能预设 hit_count=50 以避免冷启动惩罚 | — |

**决策规则：**
- SkillScore ≥ match_threshold → 命中
- SkillScore < match_threshold → 未命中，进入 L2

**⚠️ Phase 1 match_threshold 调整说明（2026-05-04 更新）：**
种子技能当前默认值 **0.25**（而非理论值 0.6）。原因：六维度中 D_semtype 固定 0.5，单关键词命中时综合得分上限约 0.39，难以达到 0.6。设置 0.25 使单关键词命中的真实 query 能够通过，同时通过同义词扩展（D_keyword）覆盖更多表达变体。D_pattern 分母取原始 keywords + aliases（不含展开同义词），避免 boost 稀释。

**Phase 2 阈值回退策略：** 积累 200+ 标注数据后，结合 L1 语义分类，逐步提升至 0.5~0.6。

**Phase 2 同义词扩展升级：** synonym_dict 扩展词库 + lightweight embedding 模型对灰区 query 做二次重排（见 Phase 2 计划）。

**⚠️ 种子技能 evolution 预设值说明：**
种子技能 YAML 中预设 `hit_count=50`、`success_rate=0.85`，目的：确保种子技能在无真实数据时通过 D_hist 维度贡献正向得分（D_hist=0.85），提升初始路由可用性。注意：hit_count=50 使 D_cold=1.0（无冷启动惩罚），预设高 success_rate 是独立的 Phase 1 演示策略，两者共同确保种子技能初始表现稳定。这些是**工程预设值，非真实运营数据**。

### 2.7 Dict 精确匹配：两级策略

实现采用两级 Dict 精确匹配策略，而非单级 token 匹配：

1. **第一级：example_queries 精确匹配**
   - 用户 query 与 `semantic_profile.example_queries` 做完整字符串匹配
   - 命中则直接返回，无需计算 SkillScore
   - 目的：覆盖"已知高置信模式"（如"借书超期了怎么办"完全匹配）

2. **第二级：token-keyword 精确匹配**
   - 对短查询（如3-5字），检查 query token 是否完整等于某技能的 keyword
   - 命中则立即返回（不走 SkillScore）
   - 目的：对高频短问句做快速精确匹配

**为何两级而非单级：**
- 单级 token-keyword 匹配会漏掉 example_queries 的语义意图
- 两级策略在"精确"和"模糊"之间取得平衡

### 2.8 同义词词典机制（v1.1）

**synonym_dict.yaml** 是 L1 的全局同义词扩展资源，位于 `skills/synonym_dict.yaml`。

#### 文件格式

```yaml
dict:
  学校:
    synonyms: [校园, 高校, 学府, 本校, 我校]
    domain: general
    confidence: 1.0
    direction: both
    note: 母校/校区暂不加——多义词，语境依赖强
  充值:
    synonyms: [圈存]
    domain: 校园卡        # 场景限定，避免与手机充值混淆
    confidence: 1.0
    direction: both
```

#### 治理字段说明

| 字段 | 值 | 含义 |
|------|-----|------|
| `synonyms` | list | 可替换标准词的同义词列表 |
| `domain` | `general` 或具体场景 | 应用范围限定，防止跨领域污染 |
| `confidence` | 0.5~1.0 | 等价确定度；<1.0 时需配合 `note` 说明适用语境 |
| `direction` | `both`（双向）或 `forward`（单向） | `forward` 表示 key→synonyms 成立，反之不保证 |

#### 加载时机

`SkillMatcher` 初始化时传入 `synonym_dict_path`，skill_loader 在加载每个 skill 时调用 `_expand_keywords_with_synonyms()`，结果写入 `skill.expanded_keywords` 字段。

#### 在各维度的作用

| 维度 | 展开后的行为 |
|------|-------------|
| **D_keyword** | 命中判断时，同义词 token 视为对标准词的命中；但分母保持为**原始 keywords 数量**（不膨胀） |
| **D_pattern**（AC automaton） | automaton 构建时使用 `expanded_keywords`，使 AC 能匹配到同义词表达；但 D_pattern 的分母仍为 `boost × len(original_keywords + aliases)` |
| **Dict tier-2** | keyword_index 使用 `expanded_keywords` 构建，实现同义词的 Dict 精确匹配 |

#### 关键设计原则

1. **分母不膨胀**：expanded 词只影响命中判断，不改变分母数值
2. **domain 隔离**：`充值` 的同义词只在 `校园卡` 场景下展开，避免泛化歧义
3. **v1.0 兼容**：`skill_loader` 自动识别 flat list 格式（v1.0）和 structured 格式（v1.1）

### 2.9 相较于原始设计的偏离（2026-05-02 实现版）

| 设计项 | 原始设计书值 | 实际实现值 | 偏离原因 |
|--------|------------|----------|---------|
| match_threshold 默认值 | 0.6（理论默认值） | **0.25**（Phase 1 运营值） | D_semtype=0.5 使单关键词命中上限约 0.39，低于 0.4；设 0.25 使真实命中的 query 通过，Phase 2 积累数据后升至 0.5~0.6 |
| 种子技能 hit_count | 0 | 50 | 绕过冷启动惩罚，保证演示效果 |
| 种子技能 success_rate | 0.0 | 0.85 | 同上 |
| Dict 匹配策略 | 单级 token 匹配 | 两级（example + token） | 实现增强，不影响功能 |

## 3. 第二层：Agentic RAG（L2）

### 3.1 LangGraph 状态图架构

```python
from langgraph.graph import StateGraph
from typing import TypedDict, List

class AgenticRAGState(TypedDict):
    query: str
    query_type: str
    router_confidence: float
    skill_config: dict  # L1 传入的检索配置
    retrieved_docs: List[dict]
    mean_similarity: float
    top1_margin: float
    doc_agreement: float
    coverage_score: float
    quality_score: float  # Q 综合质量分数
    reretrieve_count: int
    attribution_evidence: dict
    final_answer: str
```

**节点定义：**

1. **Router 节点**：LLM zero-shot 分类，输出类型 + 置信度
2. **Retriever 节点**：读取 L1 skill 配置，执行 Qdrant 检索
3. **Quality Gate 节点**：计算 Q 分数，决定通过/重检索
4. **Generator 节点**：LLM 生成最终答案

### 3.2 Quality Gate 综合质量评分

```python
Q = α·S + β·M + γ·A + δ·C
```

| 指标 | 含义 | 计算方式 |
|------|------|---------|
| S (Similarity) | 检索文档与查询的向量相似度均值 | `mean([doc.score for doc in docs])` |
| M (Margin) | top-1 与 top-2 相似度之差 | `docs[0].score - docs[1].score` |
| A (Agreement) | 检索文档之间的相关性一致性 | 文档向量余弦相似度均值 |
| C (Coverage) | 关键词实体覆盖程度 | 启发式计算，无需 LLM |

**权重建议值（Phase 1 初始值）：**
- α = 0.40, β = 0.25, γ = 0.20, δ = 0.15

**⚠️ 权重学习策略：**
Phase 1 前两周用单维度硬规则（S ≥ 0.55 且 Q ≥ 0.60），同步记录四维向量值。积累 100-200 条标注数据后用逻辑回归学习最优权重。

### 3.3 Quality Gate 决策逻辑

```python
def quality_gate_router(state: AgenticRAGState) -> str:
    Q = state["quality_score"]
    
    if Q >= 0.75:
        return "pass"  # 高置信度
    elif Q >= 0.55:
        return "pass_with_log"  # 灰色地带，标记待验证
    elif state["reretrieve_count"] < 3:
        return "reretrieve"  # 重检索
    else:
        return "pass_with_log"  # 兜底通过
```

**灰色地带（Q ∈ [0.55, 0.75)）：**
- 综合质量中等，决策不确定
- 优先进入主动探测队列
- 是最有价值的训练数据

### 3.4 attribution_evidence 输出

Quality Gate 输出归因证据字典，作为 L3 错误归因的输入：

```python
attribution_evidence = {
    "S": 0.62,                      # 检索文档与查询的向量相似度均值
    "M": 0.15,                      # top-1 与 top-2 相似度之差
    "A": 0.58,                      # 检索文档之间的相关性一致性
    "C": 0.45,                      # 关键词实体覆盖程度
    "Q": 0.58,                      # 综合质量分数
    "gap_type": "keyword_missing",  # 或 precision_dilution / doc_missing
    "top_k_max_sim": 0.62,          # top_k 中最高相似度（确定性前置筛用）
    "top1_sim": 0.62,               # top-1 相似度（确定性前置筛用）
    "has_correct_entity": False,    # 检索文档是否包含正确答案的关键实体
    "reretrieve_count": 2           # 重检索次数
}
```

**重要：** attribution_evidence 是归因的输入证据，不直接驱动技能修改。

**字段说明：**
- `top1_sim`：确定性前置筛判断"文档足够但 LLM 未用好"时使用（top1_sim > 0.80）
- `has_correct_entity`：启发式检查 top-1 文档是否包含正确答案的命名实体

### 3.7 LLM 调用容错封装

**设计原则：**
- Circuit Breaker 模式：连续失败后熔断
- 指数退避重试：1s → 2s → 4s
- 超时控制：单次调用最多 30s

```python
from enum import Enum
from typing import Optional
import time

class CircuitState(Enum):
    CLOSED = "closed"      # 正常状态
    OPEN = "open"          # 熔断状态
    HALF_OPEN = "half_open"  # 半开状态（尝试恢复）

class CircuitBreaker:
    def __init__(self, failure_threshold: int = 5, timeout: int = 60):
        self.failure_threshold = failure_threshold
        self.timeout = timeout
        self.failure_count = 0
        self.last_failure_time = None
        self.state = CircuitState.CLOSED
    
    def call(self, func, *args, **kwargs):
        if self.state == CircuitState.OPEN:
            if time.time() - self.last_failure_time > self.timeout:
                self.state = CircuitState.HALF_OPEN
            else:
                raise Exception("Circuit breaker is OPEN")
        
        try:
            result = func(*args, **kwargs)
            self.on_success()
            return result
        except Exception as e:
            self.on_failure()
            raise e
    
    def on_success(self):
        self.failure_count = 0
        self.state = CircuitState.CLOSED
    
    def on_failure(self):
        self.failure_count += 1
        self.last_failure_time = time.time()
        if self.failure_count >= self.failure_threshold:
            self.state = CircuitState.OPEN

class LLMClient:
    def __init__(self, base_url: str, api_key: str, model: str = "abab6.5-chat"):
        self.base_url = base_url
        self.api_key = api_key
        self.model = model
        self.circuit_breaker = CircuitBreaker()
    
    def call(self, messages: list, max_retries: int = 3, timeout: int = 30) -> str:
        def _call():
            # 实际调用 MiniMax API（OpenAI 兼容格式）
            import openai
            client = openai.OpenAI(base_url=self.base_url, api_key=self.api_key)
            response = client.chat.completions.create(
                model=self.model,
                messages=messages,
                timeout=timeout
            )
            return response.choices[0].message.content
        
        # 指数退避重试
        for attempt in range(max_retries):
            try:
                return self.circuit_breaker.call(_call)
            except Exception as e:
                if attempt == max_retries - 1:
                    raise e
                wait_time = 2 ** attempt  # 1s, 2s, 4s
                time.sleep(wait_time)
```

## 4. 第三层：自进化技能层（L3）

### 4.1 四步闭环流程

```
用户负反馈 → ①错误归因 → ②候选技能生成/修改 → ③冲突检测 → ④RAGAS验证+入库
```

### 4.2 错误归因：确定性前置筛 + 多裁判投票

**第一步：确定性前置筛（零 LLM）**

```python
def deterministic_attribution(attribution_evidence: dict) -> Optional[str]:
    """
    确定性前置筛：用纯数值指标过滤明确 case
    
    Args:
        attribution_evidence: Quality Gate 输出的归因证据
    
    Returns:
        "retrieval" | "generation" | None（None 表示需要进入 LLM 多裁判投票）
    """
    top_k_max_sim = attribution_evidence["top_k_max_sim"]
    top1_sim = attribution_evidence["top1_sim"]
    has_correct_entity = attribution_evidence["has_correct_entity"]
    
    # 明确的检索层问题：文档语义几乎不相关
    if top_k_max_sim < 0.45:
        return "retrieval"
    
    # 明确的生成层问题：文档足够但 LLM 未用好
    elif top1_sim > 0.80 and has_correct_entity:
        return "generation"
    
    # 模糊地带：需要 LLM 判断
    else:
        return None
```

**覆盖率：** 约 50-60% 的归因请求可被确定性前置筛直接判定。

**第二步：LLM 多裁判投票（模糊 case）**

```python
def robust_attribution(query, answer, docs, correct_answer, attribution_evidence):
    """
    LLM 多裁判投票：三个不同视角分别归因，取多数票
    
    Args:
        attribution_evidence: 作为补充证据输入，辅助 LLM 判断
    """
    prompts = [
        # 视角1：文档充分性（正向问）
        "判断检索文档是否足以回答该问题...",
        # 视角2：答案溯源（反向问）
        "正确答案的关键信息能否在文档中找到...",
        # 视角3：断言溯源（对比分析）
        "错误答案中的哪些断言在文档中无依据..."
    ]
    votes = [llm_call(p, query, answer, docs, attribution_evidence) for p in prompts]
    
    majority_result = Counter([v["layer"] for v in votes]).most_common(1)[0][0]
    confidence = max(Counter([v["layer"] for v in votes]).values()) / 3
    
    if confidence < 0.67:  # 三票全不一致
        return AttributionResult(layer=None, action="human_review")
    return AttributionResult(layer=majority_result, action="auto_proceed")
```

**⚠️ Phase 1 冷启动验证约束（必须执行）：**

在开放自动归因之前，必须先做离线验证。**关于 70% 阈值的说明：** 本项目中"归因准确率 ≥ 70%"是**基于系统冷启动风险承受能力的内部决策阈值**——低于 70% 时自动归因的误判风险超过系统可接受范围，高于 70% 时开放自动化具有工程价值。这是内部校准值，非外部学术引用标准。

```python
# 冷启动验证流程
def validate_attribution_before_launch():
    """
    Phase 1 开放自动归因前的必要验证
    
    验收标准：归因准确率 ≥ 70% 才开放候选技能生成
    """
    # Step 1: 人工构造 50 条已知根因的错误 case
    golden_cases = construct_golden_cases(
        retrieval_layer_cases=25,  # 25 条检索层错误
        generation_layer_cases=25  # 25 条生成层错误
    )
    
    # Step 2: 跑完整归因流程
    correct_count = 0
    for case in golden_cases:
        predicted_layer = full_attribution_pipeline(
            query=case.query,
            answer=case.wrong_answer,
            docs=case.retrieved_docs,
            correct_answer=case.correct_answer,
            attribution_evidence=case.attribution_evidence
        )
        if predicted_layer == case.ground_truth_layer:
            correct_count += 1
    
    accuracy = correct_count / len(golden_cases)
    
    # Step 3: 判断是否开放
    if accuracy >= 0.70:
        print("✅ 归因准确率达标，开放候选技能生成（仍需人工审核）")
        return True
    else:
        print(f"❌ 归因准确率 {accuracy:.2%} < 70%，暂不开放自动流程")
        print("建议：调优 prompt 和阈值，重新验证")
        return False
```

**Phase 1 约束：**
- 归因准确率 < 70%：只做人工审核，不开放候选技能生成
- 归因准确率 ≥ 70%：开放候选技能生成，但仍需人工审核才能入库

### 4.3 检索层问题精确归因

| 子类型 | 判定标准 | 修复动作 |
|--------|---------|---------|
| 关键词缺失 | 相关文档未排在靠前位置 | 更新 boost_keywords |
| 精度稀释 | 大量低相关性文档(<0.40) | 收紧 filter_metadata |
| 文档缺失 | 相关文档完全缺失 | 触发 ETL 补全 |
| 技能膨胀 | 技能库增长率超阈值 | 触发再平衡流程 |

### 4.4 冲突检测

```python
C = 0.4 × Jaccard(depends_on) + 0.3 × Dice(trigger) + 0.3 × Co_occur
```

| 阈值 | 级别 | 动作 |
|------|------|------|
| C ≥ 0.8 | BLOCK | 阻止入库，人工处理 |
| C ≥ 0.65 | WARN | 触发人工审核 |
| C < 0.65 | OK | 允许入库 |

### 4.5 用户反馈四通道触发机制

1. **显式通道**：用户点击"没用"按钮
2. **隐式通道**：1小时内重复提问 ≥ 3次
3. **主动探测通道**：低置信度答案 1% 概率附加探针
4. **合成反馈通道**：每周 RAGAS 自动评估技能库

## 5. 分级验证策略

### 5.1 ScaleRisk(t) 连续风险指数

```python
ScaleRisk(t) = 0.20·R_scale + 0.25·R_conflict + 0.15·R_new + 0.20·R_error + 0.20·R_synthetic
```

| 分量 | 含义 | 计算公式 |
|------|------|---------|
| R_scale(t) | 规模风险 | `min(skill_count(t) / SKILL_COUNT_MAX, 1.0)` |
| R_conflict(t) | 冲突风险 | `avg_conflict_score(t)`（来自 ConflictDetector） |
| R_new(t) | 新增风险 | `new_skill_count_30d / skill_count(t)` |
| R_error(t) | 错误率风险 | `1 - avg(success_rate)` |
| R_synthetic(t) | 合成反馈速率 | `min(synthetic_cases_last_week / 10, 1.0)` |

**权重说明：**
- R_conflict 权重最高（0.25）：冲突是最直接的风险信号
- R_synthetic 权重 0.20：监控系统自检能力，过低触发告警

**合成反馈速率告警：**

```python
def check_feedback_health(R_synthetic: float, real_feedback_rate: float):
    """
    监控系统进化燃料是否充足
    
    Args:
        R_synthetic: 合成反馈速率（0~1）
        real_feedback_rate: 真实用户反馈速率（条/周）
    """
    if R_synthetic < 0.1 and real_feedback_rate < 5:
        alert("⚠️ 系统缺乏进化燃料：合成反馈和真实反馈均极低")
        alert("建议：增加 RAGAS 自动评估频率或主动探测概率")
```

### 5.2 三级验证阈值

- ScaleRisk < 0.40 → 低风险：自动记录 + 随机抽检
- ScaleRisk ∈ [0.40, 0.65) → 中风险：RAGAS + 相似 query 回放
- ScaleRisk ≥ 0.65 → 高风险：Golden Query Set + RAGAS + 人工审核

```python
def get_validation_level(scale_risk: float) -> str:
    if scale_risk < 0.40:
        return "low"    # 自动记录 + 10% 随机抽检
    elif scale_risk < 0.65:
        return "medium" # RAGAS 验证 + 相似 query 回放
    else:
        return "high"   # Golden Query Set + 人工审核
```

## 9. 关键设计决策记录

### 9.1 为什么用 YAML 存储技能？

- 人类可读，便于审核
- Git 版本管理友好
- 支持注释和多行文本

### 9.2 为什么 Phase 1 不用 embedding？

- 降低冷启动复杂度
- 纯文本匹配已能覆盖高频问题
- Phase 2 再引入语义召回

### 9.3 为什么需要确定性前置筛？

- 压缩 LLM 归因的利益冲突空间（LLM 判断自己的错误存在偏见）
- 覆盖 50-60% 的明确 case，降低归因成本
- 提高归因准确率（确定性规则 + LLM 判断的组合优于纯 LLM）

### 9.4 为什么 ScaleRisk(t) 需要 R_synthetic 分量？

- 监控系统自检能力：合成反馈是进化的燃料
- 当 R_synthetic < 0.1 且真实反馈也极低时，系统将无法持续优化
- 触发告警机制，提醒增加 RAGAS 评估频率或主动探测概率

### 9.5 为什么需要冷启动验证约束？

- 归因错误会污染技能库，导致系统性能下降
- 50 条 golden case + 70% 准确率是开放自动归因的最低门槛
- Phase 1 必须先验证归因可靠性，再开放候选技能生成

## 11. 实验基线系统说明

### 11.1 naiveRAG 的架构定位

naiveRAG（朴素 RAG）不是 EvoRoute-RAG 架构中的独立模块，而是**系统在特定运行模式下的退化形态**：

```
L1 跳过 + skill_config=None + 跳过 Quality Gate 复杂逻辑
= naiveRAG（用户提问 → 向量检索 → LLM 生成）
```

**结论：不在架构图中增加 naiveRAG 模块。它是 EvoRoute-RAG 完整系统的一个简化子集。**

### 11.2 为什么实验必须引入 naiveRAG

尽管架构不需要，但 naiveRAG 在论文实验中扮演**不可替代的叙事功能**：

1. **建立性能下界**：作为"什么都不优化"的基线，衬托三层架构的相对增益
2. **量化自进化总增益**：`Evolved EvoRoute(Context Precision) - naiveRAG(Context Precision)`
3. **解释"为什么需要三层"的设计动机**：用数据证明 L1 零 LLM 路由和自进化闭环的价值
4. **支撑消融实验**：作为"无 L1 + 无 L3"的系统形态对照

### 11.3 三系统对比设计

| 系统 | L1 路由 | L2 配置 | L3 进化 |
|------|---------|---------|---------|
| naiveRAG（基线） | ❌ 跳过，全部直送 L2 | 无 skill 配置，vanilla RAG | ❌ 无 |
| Static EvoRoute | ✅ 种子技能路由 | Agentic RAG + skill 配置 | ❌ 无进化 |
| Evolved EvoRoute（完整） | ✅ 种子技能路由 | Agentic RAG + skill 配置 | ✅ 自进化闭环 |

### 11.4 实现方式

**naiveRAG 作为独立脚本存在，不集成到主架构代码中。**

在实验阶段另行构建于 `experiments/naive_rag_baseline.py`，不进入 `evoroute_rag/` 主代码包：

```python
# experiments/naive_rag_baseline.py（实验阶段构建，不在主代码中）
def naive_rag(query, qdrant_client, llm_client):
    docs = qdrant_client.search(query, top_k=5)
    answer = llm_client.generate(query, docs)
    return answer
```

L2 LangGraph pipeline 中通过 `pipeline_mode` 配置开关切换：
- `pipeline_mode = "full"` → 完整三层系统
- `pipeline_mode = "naive"` → 跳过 L1、跳过 skill 配置、跳过复杂 Quality Gate

### 11.5 论文中的表述方式

在实验章节（不是第三章技术架构部分）说明：

> *本实验构建三种对比系统：(1) naiveRAG——直接向量检索+LLM生成，无技能路由、无进化；(2) Static EvoRoute——含种子技能的静态三层系统；(3) Evolved EvoRoute——本文提出的完整方案。*
